# ワーキングアグリーメント

チーム全員（人間も AI も）が守る約束。

## 1 PR で必ずやること

1. ユニットテストを書く
2. 静的コード解析を通してからコミットする（pre-commit で自動実行される。`--no-verify` で飛ばさない）
3. ドキュメントを更新する

## 完了の定義（DoD）

- [ ] 受け入れ基準を満たす
- [ ] ユニットテストがあり、`npm run check` が通る
- [ ] CI が通る
- [ ] 関係するドキュメント（`docs/`、README）を更新した
- [ ] 1 人以上がレビューした（CODEOWNERS で自動で付く担当者）

## 受け入れ基準

Issue には Given-When-Then で書く。

```
Given: active なタスクが 5 件ある
When:  3択画面を開く
Then:  3 件のタスクが表示され、1 件だけ選べる
```

## 着手前に決めること

- **API とデータ構造**: フロントとバックを別の人が作るときは、先に `docs/api.md` と `src/lib/schemas.ts` を更新する PR を出して合意する
- **破壊的変更**: DB スキーマや `src/lib/` の共通部分を変えるときは、影響を受ける担当者に PR で共有する
- **粒度**: 1〜2 日で PR を出せる大きさに分ける。調べないと進め方がわからないものは、実装とは別の調査タスク（スパイク）にする
- **依存関係**: 他の人の成果物を待つ必要があるかを Issue に書く（`docs/team.md` の依存関係も参照）

## ブランチとコミット

- `main` に直接 push しない。ブランチを切って PR を出す
- ブランチ名: `<種類>/<内容>`（例: `feat/quest-candidates`、`fix/checkpoint-order`、`docs/setup`）
- コミットメッセージ: `<種類>: <内容>`（例: `feat: 3択の候補取得 API を実装`）。種類は `feat` / `fix` / `docs` / `test` / `refactor` / `chore`
- マージは Squash and merge。マージ後のブランチは削除する
- コンフリクトを避けるため、作業前に `main` を取り込む（`git pull origin main` または rebase）
