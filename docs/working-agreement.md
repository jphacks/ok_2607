# ワーキングアグリーメント

チーム全員（人間も AI も）が守る約束。

## Issue と PR の対応

- 作業は Issue を起点にする。同じ目的の Issue があれば再利用し、無ければ AI がタスクテンプレート（`.github/ISSUE_TEMPLATE/task.md`）に沿って作成し、`task` ラベルを付ける
- Issue には作業内容と Given-When-Then の受け入れ基準を書き、Assignee を依頼者にする。既存のバグ報告には再現手順を生かして受け入れ基準を補う
- 担当範囲は `docs/team.md` に従う。作業中に見つけた範囲外の改善・不具合は別 Issue に記録する
- 受け入れ基準をすべて満たす最後の PR の本文に `Closes #番号` を書く。デフォルトブランチ（`main`）へのマージ時に Issue が自動で閉じる
- 段階的な実装や共通部分の先行 PR は `Refs #番号` を使う。最後の PR がマージされるまで Issue を開いたままにする

## 1 PR で必ずやること

1. ユニットテストを書く
2. 静的コード解析を通してからコミットする（pre-commit で自動実行される。`--no-verify` で飛ばさない）
3. ドキュメントを更新する

## 完了の定義（DoD）

- [ ] 受け入れ基準を満たす（部分実装なら、残作業を Issue に明記して `Refs #番号` で関連付ける）
- [ ] PR 本文に関連 Issue を書いた（全基準を満たす最後の PR は `Closes #番号`）
- [ ] ユニットテストがあり、`npm run check` が通る
- [ ] CI が通る
- [ ] 関係するドキュメント（`docs/`、README）を更新した
- [ ] AI レビューが PASS した（`docs/ai-review.md`）。人の承認は不要

## マージ

- CI と AI レビューが通った PR は、人の承認なしでマージしてよい。AI がマージしてもよい
- `main` はブランチ保護で「PR 必須・CI 必須・最新の `main` を取り込んでいること」を必須にしている。CI が通らない PR や、`main` から遅れている PR はマージできない（遅れていたら `gh pr update-branch <番号>` で取り込む）
- AI レビューは各自の AI がローカルで、実装とは別のコンテキスト（サブエージェント）で行う。結果は PR の説明に貼る
- AI レビューの PASS は GitHub 側では強制していない（自己申告）。PR の説明に結果が無い、または FAIL のまま出ている PR を見つけたら指摘する
- リポジトリ設定で、マージ方法は Squash のみ、マージ後のブランチは自動削除にしている
- CODEOWNERS の担当者には PR の通知が届く。気になる点があればマージ後でも Issue や PR で伝える

## 受け入れ基準

Issue には Given-When-Then で書く。

```
Given: active なタスクが 5 件ある
When:  3択画面を開く
Then:  3 件のタスクが表示され、1 件だけ選べる
```

## 着手前に決めること

- **API とデータ構造**: フロントとバックを別の人が作るときは、先に `docs/api.md` と `src/lib/schemas.ts` を更新する PR を出して合意する
- **破壊的変更**: DB スキーマや `src/lib/` の共通部分を変えるときは、影響を受ける担当者に PR で共有する
- **共通ファイルは先に別 PR**: `schemas.ts`・`globals.css`・`tokens.css`・`src/components/ui/`・マイグレーションなどの共通ファイルの変更は、機能の PR に混ぜず先に小さい PR で出す（対象の一覧は `AGENTS.md`「共通ファイルと PR の大きさ」）
- **見た目**: 画面は `docs/design.md` のトークンと共通部品で作る。各自の AI に任せると見た目がばらつくため
- **粒度**: 1〜2 日で PR を出せる大きさに分ける。調べないと進め方がわからないものは、実装とは別の調査タスク（スパイク）にする
- **依存関係**: 他の人の成果物を待つ必要があるかを Issue に書く（`docs/team.md` の依存関係も参照）

## ブランチとコミット

- `main` に直接 push しない。ブランチを切って PR を出す
- ブランチは必ず最新の `main` から切る。マージ前の他のブランチから派生させない（Squash マージ後にコンフリクトするため）
- ブランチ名: `<種類>/<内容>`（例: `feat/quest-candidates`、`fix/checkpoint-order`、`docs/setup`）
- コミットメッセージ: `<種類>: <内容>`（例: `feat: 3択の候補取得 API を実装`）。種類は `feat` / `fix` / `docs` / `test` / `refactor` / `chore`
- マージは Squash and merge。マージ後のブランチは削除する
- コンフリクトを避けるため、作業前に `main` を取り込む（`git pull origin main` または rebase）
