# AI レビュー

すべての PR は、マージ前に AI レビューを通す。人の承認は不要。

## 仕組み

- レビューは**実装した会話とは別のコンテキスト**で行う。同じ会話でレビューすると、自分の書いたコードに甘くなるため
- 人がセッションを切り替える必要はない。実装した AI がサブエージェント（Claude Code なら `code-reviewer`）を呼び出してレビューさせる
- Claude Code では `/ship` を実行すると、チェック → AI レビュー → 修正 → PR 作成 → 自動マージの予約まで進む
- サブエージェント機能が無いツールでは、別プロセス（例: `claude -p`、`codex exec`）にこのファイルと差分を渡してレビューさせる

## レビュー観点

上から順に重要。**ブロッカー**が 1 つでもあれば FAIL。

### ブロッカー（直さないとマージできない）

1. **バグ**: 明らかに誤った動作、例外の握りつぶし、境界値の誤り、非同期処理の `await` 漏れ
2. **セキュリティ**: 秘密の値のコミット・ログ出力、クライアントからのサーバー専用モジュールの import、入力検証の欠落、新しいテーブルの RLS 未設定
3. **AGENTS.md のルール違反**
   - ユニットテストが無い（ロジックの追加・変更に対して）
   - `src/lib/schemas.ts` と `docs/api.md` の不一致
   - 適用済みのマイグレーションファイルの編集
   - `any` / `@ts-ignore` を理由なく使用
   - MVP の範囲外の機能（ログインなど）
4. **他人の担当範囲の無断変更**（`docs/team.md` 参照）。PR の説明に共有した旨があれば可

### 指摘のみ（直すのが望ましいが FAIL にしない）

- 読みやすさ、命名、重複、もっと簡単に書ける箇所
- テストケースの不足（主要な経路はテストされている場合）
- ドキュメントの軽微な更新漏れ

## 出力形式

```
## AI レビュー結果: PASS | FAIL

### ブロッカー
- `path/to/file.ts:42` 問題の説明と、どう直すべきか
（なければ「なし」）

### 指摘
- `path/to/file.ts:10` 内容
（なければ「なし」）

### 確認したこと
- 差分の範囲: <base>...<head>（変更ファイル数）
- `npm run check`: 成功 / 失敗
```

この結果を PR の説明の「AI レビュー」欄にそのまま貼る。

## 修正のループ

1. FAIL ならブロッカーを直し、`npm run check` を通してから、もう一度レビューさせる
2. 3 回レビューしても PASS にならなければ、PR を作らずに止めて人に判断を求める
3. レビュアーの指摘が誤りだと考える場合も、PR を作らずに止め、理由を添えて人に判断を求める（AI だけで却下しない）
4. PASS した後にコードを変えたら（CI の修正を含む）、必ずレビューを受け直し、PR 本文の結果を更新する
